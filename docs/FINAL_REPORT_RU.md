# Итоговый отчёт по сканеру российских вин

## Что готово

Рабочий локальный прототип включает аудит данных, обученную модель, поисковый индекс, API, OCR-диагностику, мобильную веб-страницу и функцию рекомендации к блюду. Контракт организатора поддержан: `POST /v1/eval/predict`, multipart-поле `image`, ответ `{"slug":"..."}`. Веб-интерфейс находится на `http://127.0.0.1:8080/` после запуска `scripts/run.ps1`.

## Как обучена модель

Основа — `google/siglip2-base-patch16-384`, revision `f775b65a79762255128c981547af89addcfe0f88`, SHA256 весов `ed72c0ace85020ae610fc817c2538b9cae5a477b012a50859c60af5b3ad30857`. Энкодер заморожен.

Поверх 768-мерного вектора обучен остаточный MLP-адаптер 768 → 256 → 768, 394240 параметров. Для каждого вина используются два эталонных вида: бутылка и эвристическая область этикетки. Положительные запросы создаются перспективой, поворотом, яркостью, контрастом и размытием. Источники делятся по хешу 70/15/15: train 1382, validation 295, test 293. Производные одного источника не пересекают части. Обучение: AdamW, LR 1e-4, weight decay 0.01, температура 0.07, seed 42, 15 эпох; выбрана эпоха 13 по validation Accuracy@1.

## OCR-эксперимент

Для 1970 эталонов построен локальный OCR-индекс. OCR-only на синтетическом test: Accuracy@1 42.32%, macro-F1 44.87%. Проверка весов объединения на validation выбрала вес OCR 0. Глобальное OCR-переранжирование отключено: оно ухудшало результат. OCR остаётся сигналом несогласия для статуса `low_confidence_reshoot`.

SIFT/RANSAC также проверен отдельно. Он совпадает по общему оформлению серий, но не различает мелкие надписи; в основной API не включён.

Оборудование: NVIDIA GeForce RTX 5070, PyTorch 2.11.0+cu128. CUDA проверена вычислением и обучением. Индекс содержит 3940 векторов: по два на каждый из 1970 slug.

## Публичные фотографии

Все три запроса прошли API, но ответы организатора закрыты, поэтому публичные Accuracy и F1 неизвестны. Ручное чтение этикеток и CSV показывает:

- q-000001: «Табия Пино Нуар 2025» — винодельня есть, точной карточки нет;
- q-000002: «Мускатель Массандра белый» — точная карточка есть, CV путает похожую серию;
- q-000003: «ARISTOV DONUM XXIV брют 2023» — бренд есть, точной карточки нет.

Это объясняет, почему нельзя честно заявить 90–100% на публичных/приватных полевых данных. Текущий продуктовый API помечает такие случаи как недостаточно уверенные; оценочный endpoint всё равно возвращает ближайший slug по обязательному контракту.

## Как работает запрос

1. Фото разворачивается по EXIF, приводится к RGB; строятся четыре центральных масштаба.
2. SigLIP 2 получает признаки, обученный адаптер усиливает различимость вин.
3. Каждый запрос сравнивается косинусной мерой с двумя эталонными векторами каждого slug.
4. Лучшие виды объединяются по slug. Разница top-1/top-2 используется как диагностическая уверенность.
5. OCR читает текст и строит свой список. Из-за слабых метрик он не меняет slug, но несогласие снижает продуктовый статус.
6. `/v1/eval/predict` возвращает плоский slug; `/v1/predict` возвращает карточку, кандидатов, статус и диагностику.
7. После карточки пользователь может указать блюдо и получить прозрачную рекомендацию по категории/сорту.

## Что ещё нужно для пилотного качества

Главный следующий набор данных — 300–500 размеченных реальных фото с точными slug, включая похожие серии, годы и отсутствующие вина. После этого нужно исправить каталог, обучить/подключить русскоязычный OCR на обрезках этикеток, подобрать fusion и порог отказа только на полевых validation, а затем один раз измерить закрытый test. Без этого синтетические 93.17% нельзя переносить на магазинные условия.
